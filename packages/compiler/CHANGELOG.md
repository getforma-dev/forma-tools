# Changelog

## [Unreleased]

## [0.3.7] - 2026-10-14

Release A2, the bridge to 3.0.0: additive, with deprecations. Released with
`@getforma/build` 0.3.1, whose `--strict` needs this version.

### Upgrading from 0.3.6: what an application may meet

- **Each `IR:` warning carries a code and a position** (`IR: BUILD-101 ...
  in /app/src/home/app.tsx:12:11 — ...`). The text around them is 0.3.6's,
  with a few deliberate exceptions (`docs/DIAGNOSTICS.md`, "What a diagnostic
  looks like"): three page-level lines now name the entry, a literal past
  65,535 bytes is reported where it is written, BUILD-701 to BUILD-707 word
  their constructs anew, and **BUILD-303 adds a line** for a `createList`
  over a plain read of a signal initialised with literal rows. A gate that
  counts or matches these lines should be checked against the new text.
- **The same modules.** A page that does not use `browserOnly()` compiles to
  the same bytes; `npm run emit:corpus` emits the same 14 modules.
- **Deprecation lines, once per process:** creating `formaCompiler` or
  `formaServer`, and the first call of `transformServerFunctions`
  (`BUILD-901`).
- **`formaCompiler`'s output routes URL attributes through core's guard**
  (Security): a `javascript:` URL it used to write is dropped, as runtime
  `h()` drops it.

### Added
- **`DIAGNOSTIC_CATALOGUE` carries the preview frame's codes, `BUILD-805` to `BUILD-807` (FORMA-175).** `@getforma/build`'s `previewFrame` reports them when the `@getforma/core` the bundles import has no `dist/formajs-frame.global.js` (`BUILD-805`), when that runtime cannot be inlined as forma-server's `PreviewFrame::load` inlines it (`BUILD-806`: empty, not UTF-8, `</script`, `<!--`, a carriage return or a NUL), and when the bundles import more than one core whose frame runtimes differ (`BUILD-807`). Each is an error that fails the build with or without strict mode; none is a note. `docs/DIAGNOSTICS.md` documents them (`tests/diagnostics-conformance.test.ts` keeps the catalogue and the page equal; no code can be written as a page, so each is tested in `packages/build/tests/preview-frame.test.ts`).
- **`DIAGNOSTIC_CATALOGUE` carries the raw-entry lint's codes, `BUILD-810` to `BUILD-814` (FORMA-126, SR8).** `@getforma/build`'s `forma-raw-lint` reports them (a raw entry not on the allowlist, an entry past its end date, an allowlist it cannot use, an entry that lists nothing, a source it cannot parse); they are never in a build's report. `BUILD-813` is a note, as the deprecations are. The compiler's behaviour is unchanged. Tests: `tests/diagnostics-conformance.test.ts` (the catalogue and `docs/DIAGNOSTICS.md` checked against each other, as for every code) and the build package's `tests/raw-lint.test.ts` > "the compiler catalogue and docs/DIAGNOSTICS.md carry BUILD-810 to BUILD-814 as the lint reports them".
- **Coded build diagnostics (FORMA-119; DR-1 migration step 1, L-3, N12).** Every construct the compiler cannot represent in a server-rendered module (rule 11's anonymous islands, dropped attributes and text, unmatched children, dynamic tags, components from a package or past the 3-level inlining limit, placeholder modules, a literal past 65,535 bytes, unnamed signals) is reported with a stable code numbered by family (`BUILD-101` to `BUILD-901`, 56 codes in 9 families; the build package reports `BUILD-801` to `BUILD-807` (`BUILD-805` to `BUILD-807` its preview frame, FORMA-175, below), its raw-entry lint `BUILD-810` to `BUILD-814` (FORMA-126, above), and `BUILD-901` is `transformServerFunctions`' deprecation, FORMA-131), the file, the line and the column, one line of why and one of fix. `docs/DIAGNOSTICS.md` documents each code; `DIAGNOSTIC_CATALOGUE` exports them; `collectDiagnostics(fn)` returns those reported while `fn` runs.
  - **The default output does not change but for the code and the position.** Each report prints the line 0.3.6 printed, one `console.warn` per construct, with the code after `IR:` and `:line:column` after the file; no line is added or removed, so GateWASM's per-file count and ksx Studio's text matches see what they saw. Exceptions: `inline return node is not a call expression`, `real emission failed` and the module-write failure now name the entry file (the last also starts with `IR:`); a literal past 65,535 bytes is reported where it is written (`BUILD-604`) instead of as `real emission failed`; the constructs below get their own wording; and **`BUILD-303` adds a line** where 0.3.6 printed none, for a `createList` over literal rows (below), so a gate that counts these lines sees one more per such list (GateWASM `b750ca5` and ksx Studio `0cb57e2` have none).
  - **Positions in `.tsx` and `.jsx` are the author's.** The JSX transform's source map (esbuild, `sourcemap: 'external'`, whose code is byte-identical to a transform without one) takes a node's position back to the line written.
  - **`BUILD-403` names the composition chain** from the page down (`(chain: HomePage > Layout > Card > Panel > Badge)`, and `chain` in the data), so composition past the inlining limit can be counted in strict mode (L-26).
  - **FORMA-016's constructs are reported under their own codes, naming `browserOnly()` as the way out:** a plain array child (`.map()` without `createList`, `BUILD-701`), `createErrorBoundary` (`702`), `createSwitch` (`703`), `createPortal` (`704`) and `createSuspense` (`705`), which were reported as a call, a text child or a component the compiler could not resolve. Each line says what the construct does after activation, measured in Chromium on a `mount()` root: `createErrorBoundary`, `createSwitch` and `createSuspense` make activation throw (`insertBefore`) so nothing after them activates; `createPortal`'s content never appears; a plain `.map()` child's rows never appear, and in a reactive child the page shows its elements as `[object HTMLLIElement]` text. What is emitted for them does not change; adoption support is 3.0.0's decision.
  - **Notes, which strict mode never fails on:** `BUILD-504` and the deprecations whose old paths keep working in A2 (`BUILD-802` to `BUILD-804`, FORMA-130 and FORMA-131's build options and wasm-pack step, and `BUILD-901`), catalogued so the catalogue is complete; a build that still sets `wasm` passes in strict mode.
  - **`BUILD-504` is a note:** a signal initialized with a literal array or object still gets no named slot and its line is still printed, but DR-1 admits it, so strict mode never fails on it. A read in text, an attribute or a conditional is reported where it is (`301`, `206`, `302`), and a `createList` whose source is a plain read of literal rows as `BUILD-303` (below); a derived source is not detected in A2.
  - **`BUILD-303`: a `createList` over a signal initialized with literal rows** (`createSignal([{…}, …])`, declared in the file or imported from a store module), when the list's source is a plain read: `rows`, `rows()` or `() => rows()`. A derived source over literal rows, such as `createList(() => rows().filter(…))`, is not detected in A2 (widening it is 3.0.0's subset work, FORMA-101). The rows have no slot, so the server renders the list empty unless a handler fills `list:<name>:array`, while the browser renders the rows; an error in strict mode. A `createList` over `createSignal([])` is not reported: both sides start empty. What is emitted does not change.
  - **`formaSsrPlugin` takes `strict` and `onDiagnostics`.** With `strict`, each diagnostic but a note becomes an esbuild error at its file, line and column, with its why and fix as notes; the module is still written. `@getforma/build` 0.3.1 applies strict mode itself, across every page.
- **`browserOnly()`, the browser-only marker (DR-1, L-1).** A component declared `const X = browserOnly(Impl)` (from `@getforma/core`, which exports it from 2.1.0) is emitted as a registered island named as the call names it, whose server output is its empty host element with its declared props: the props it can evaluate to a string, number, boolean or null, written as the host's `data-forma-props` (a prop it cannot evaluate, or one named `__proto__`, `constructor` or `prototype`, which core strips from island props, is `BUILD-706`). The declaration is followed through relative imports and re-exports, never into a package; the component is never walked, so it is an island at any depth and with any props. On a page whose `activateIslands` registry does not name it, `BUILD-708`; `browserOnly(...)` called inside the tree, `BUILD-707`. The marker is looked for only where the walk would otherwise give up on a component, so a page that does not use it compiles to the same bytes.
- Tests: `tests/diagnostics-conformance.test.ts` (per code, a fixture under `tests/fixtures/conformance/<code>/fail` that reports it at every marked line and nowhere else and fails an esbuild build under `strict` at that file and line, and a near miss under `pass` that reports nothing and builds under `strict`; the catalogue, the fixtures and `docs/DIAGNOSTICS.md` checked against each other; `BUILD-606` by an unwritable output and an unreadable entry; the source-map position; the 403 chain) and `tests/browser-only.test.ts`. The 14-case FMIR corpus is byte-identical to 0.3.6's.

### Changed
- **Release and CI install with `npm ci` (DR-32, FORMA-010; the package is unchanged).** `release.yml`, `ci.yml` and `compat.yml` install exactly what `package-lock.json` records instead of running `npm install`; `compat.yml` still installs the newest `@getforma/core` on top, deliberately. Each `uses:` names the commit its tag or branch pointed to on 2026-10-14, with the ref in a comment, and every CI job declares `contents: read`; `release.yml` keeps its workflow-level `contents: read` and `id-token: write`.
- **Only the release's publish job can mint the publish credential (SR43, L-34, L-42, FORMA-134; the package is unchanged).** `release.yml` splits into `test`, `pack` and `publish`. Tests and builds run in jobs without `id-token: write`; `pack` restores no cache, packs the tagged package with `npm pack --ignore-scripts` and records its SHA-256; `publish`, the only job holding `id-token: write`, restores no cache and installs nothing, checks the downloaded tarball against that record (whose own hash travels as a job output) and runs `npm publish <tarball> --provenance --access public --ignore-scripts`. A `build-v*` release now also runs the compiler's suite, as CI does. The tags stay the only trigger. CI's new `release-workflow` job runs actionlint (binary checked against a pinned SHA-256), `scripts/check-release-workflow.rb --self-test` and `scripts/test-release-artifacts.sh`. The lint also refuses a publish job that could go on after a failed check (`continue-on-error`, an `if:` on a step up to the publish, `always()`, `failure()` or `cancelled()` in the job's `if`, a check line that can swallow its failure, a shell without errexit), `container:` or `services:` on the publish or pack job, and a checkout of another repository or ref; every rule has a seed in `--self-test`, which fails if one does not. The artefact test flips a byte instead of writing one that may already be there. `pack`'s setup-node sets `package-manager-cache: false`, so a move to setup-node v5 keeps its cache off.
- **CI installs Chromium in two bounded steps (FORMA-179; the package is unchanged).** The `e2e` job installs Chromium's system packages, then the browser, each restored from a cache keyed on the Playwright version (the packages' also on the runner image) and each cut at a bound with one retry, where `npx playwright install chromium --with-deps` had only the job's timeout: a slow apt mirror once held formajs's WebKit install past its job's. CONTRIBUTING says which skipped checks are by design.
- **The release's artefact upload can be re-run (A2 audit S7, FORMA-179; the package is unchanged).** The release's `pack` job uploads `release-packed` with `overwrite: true`, so re-running all jobs after a failure replaces the earlier attempt's artefact instead of failing on its name (A2 audit S7); `publish` still checks every file against the record whose hash `pack` passes as a job output. The SR43 lint's new rule K4 requires it, with two seeds in `--self-test`.

### Deprecated

Each keeps working through 0.3.x, logs its deprecation, and goes in 3.0.0:

| Deprecated in 0.3.7 | Use instead (3.0.0's form) |
|---|---|
| the Vite plugin `formaCompiler` (compiled output) | `@getforma/build`, which keeps runtime `h()` |
| the Vite plugin `formaServer` | a route in the application's Rust server (server functions go in 3.0.0) |
| `transformServerFunctions`, the `"use server"` transform (`BUILD-901`) | a route in the application's Rust server |

- **The Vite plugins `formaCompiler` and `formaServer` are deprecated, and are removed in 3.0.0 (L-23).** Each logs a deprecation naming 3.0.0, once per process, when it is created.
  - `formaCompiler`'s compiled output does not behave like runtime `h()`. Probes against core 2.0.1 in FORMA-007's review found that an island hydrated over server markup gets no handlers or updates, a signal getter as a child renders as source text, style objects are dropped, and more. The README now says the path is unsupported and why.
  - `formaServer` goes with server functions (DR-22).
  - No application of the stack uses either plugin. `@getforma/build`, which keeps runtime `h()`, is the supported build, and nothing that `formaSsrPlugin` or the FMIR emitter does changes.
- **`transformServerFunctions`, the `"use server"` transform, is deprecated, and is removed in 3.0.0 with server functions** (FORMA-131; DR-22), as `@getforma/core/server` is in core 2.1.0. Its first call in a process logs `[@getforma/compiler] BUILD-901 transformServerFunctions, the "use server" transform, is deprecated…`, whatever the module holds, and it is marked `@deprecated`. What it writes is unchanged, and so is the FMIR corpus: `npm run emit:corpus` emits the same 14 modules byte for byte. `formaServer` runs it, so a `formaServer` build now logs this line as well as the plugin's own. BUILD-901 opens a family for the compiler's own deprecated entry points, BUILD-9xx, documented in `docs/DIAGNOSTICS.md` with the rest of the catalogue. Test: `tests/server-transform-deprecation.test.ts` > "transformServerFunctions logs BUILD-901 once, naming 3.0.0" (which also checks the stub and the registration are still written). `tests/formajs-contract.test.ts` keeps the line out of its output, as the plugins' tests do.

### Security
- **`formaCompiler`'s output no longer bypasses core's attribute guard.** It used to write, with its own `setAttribute`, a URL attribute whose value came from a variable or a getter, so `href: url` with `url = 'javascript:alert(1)'` was written where runtime `h()` drops it. It also baked a static `javascript:` URL and a static `ONCLICK` string into the template, and ran a lowercase `onclick` function at render.
  - An element carrying any of these is now left to runtime `h()`, which applies core's guard on the first render and on every reactive update: a URL attribute (`href`, `src`, `action`, `formaction`, `xlink:href`, `poster`, `background`, `data`, any case) whose value is not a literal, such an attribute whose literal value has a scheme, or an `on…` attribute that is not an `onX` listener.
  - Literal relative URLs still compile into the template.
  - A tag or attribute key that fails core's name pattern (`/^[A-Za-z_:][-A-Za-z0-9_:.]*$/`, its `isSafeTagName` and `isSafeAttrName`) is left to runtime `h()` as well. The template wrote names verbatim, so `'href '`, `'x onclick'` or a tag `'img src=x onerror=…'` added an attribute no guard saw. Runtime `h()` then throws at render, as it does without the plugin; the compiler does not refuse it at build, since it leaves every construct it cannot compile (a dynamic tag, a spread, a computed key) to runtime `h()`.
  - Core does not export its guard, so the compiler defers to it rather than copying its rules. Compiled output imports nothing new from `@getforma/core`.
  - Tests: `tests/vite-plugin-deprecation.test.ts` covers the attributes left to `h()`, the ones still compiled, the surrounding tree still compiled, and the deprecation logged once. `e2e/compiled-url-guard.spec.ts` > "a compiled module writes no javascript: href from a variable, and keeps safe ones (FORMA-019)" compiles a module with this compiler and runs it in Chromium against FormaJS. Before this change it failed: `<a href="javascript:alert(1)">`.

## [0.3.6] - 2026-10-14

### Changed
- **The Vite plugins' output imports `@getforma/core`, never the bare `formajs`.** Only the output of the Vite plugins `formaCompiler` and `formaServer` changes: `formaCompiler`'s template transform imports `template` and `createEffect` from `@getforma/core`, and `formaServer`'s stubs and registrations import from `@getforma/core/server`; both entry points are in `@getforma/core` 2.0.1's `exports`. `@getforma/build` and the FMIR that `formaSsrPlugin` emits are untouched. The bare name resolved only where a build aliased it (`@getforma/build`'s `formaAlias`, or a Vite `resolve.alias`), and npm refuses to publish `formajs` to anyone because it is too similar to the third-party `forma-js`, so it can never be claimed and only an alias stands between a compiled import and a missing package. A module's own `formajs` imports are left as written, and `formaAlias` still resolves them. Setup to check when upgrading: a project that resolves `formajs` to anything other than the installed `@getforma/core` (a Vite alias to a local path, `npm link`, or a `file:` dependency named `formajs`) must now make `@getforma/core` itself resolve, since compiled modules name it directly. Rollback: pin 0.3.5. Tests in `tests/formajs-contract.test.ts` pin every emitted specifier, among them "adds no import of the bare name \"formajs\", even to a module written against it"; each went red with its specifier reverted.

## [0.3.5] - 2026-08-07

### Fixed
- **Import resolution no longer mints slots for store signals nobody reads.** Whole-frame entry — the 0.3.2 design — gave every evaluable signal in an imported-from module a slot at root-scope time, bloating the slot table and letting an UNREAD store signal claim a base slot name ahead of a later-inlined component's own signal (which then shipped as `name#2`, breaking name-addressed injection expectations). Frames entered by import resolution are now LAZY: they carry the module's complete declaration map (the memo contract is about the map, not the slots) and a declaration only materializes when an import actually names it — or when the walk enters the module as a component, which upgrades the frame in place, so a file that is both a store and a component still has exactly one frame and one slot per signal. Unread signals cost nothing; a component's `count` keeps the name `count` when the store's `count` is never imported; the collision warning still fires for real collisions at materialization. One nuance: for a both-imported-and-walked module, slot IDs follow materialization order (imported names first) — names and defaults are unchanged, and injection is by name. Three new tests (no-slot-for-unread, no-name-stealing, mixed-entry upgrade), the first two red with the change reverted; 14/14 corpus `.ir` byte-identical.

## [0.3.4] - 2026-08-07

### Fixed
- **Two residual variants of the 0.3.3 guards, found by adversarial probes of the shipped fixes.** (1) `nestedScopeBindings` collected const/param/catch shadows but not nested `function name() {}` or `class name {}` declaration ids, so a component declaring `function tok() {…}` while its file imported signal `tok` still folded the store's default at the `tok()` read — the exact silent-wrong-SSR failure the 0.3.3 shadowing guard exists to stop, one declaration form over. Declaration ids below module top level are now collected, which also tightens the string-constant fold that shares the helper. (2) The signal export walk ignored `exportKind`: `export type { tok } from './store'` — and the inline `export { type tok }` — was followed as a value edge, folding the store's default and minting its slot table for an import that cannot exist at runtime. Both forms are now skipped. Four new tests, each red with its guard reverted; 14/14 corpus `.ir` byte-identical.

## [0.3.3] - 2026-08-07

### Fixed
- **An imported signal folded through a shadowing local — a silently wrong SSR value where 0.3.1 shipped a flagged degradation.** The scope chain only carries `createSignal` declarations, so a component-local `const status = () => …` was invisible to `lookupSignal` and a page that both imported `status` and declared its own resolved every read to the STORE's default. The import scan now consults `nestedScopeBindings` (the same guard the imported-const resolver has had since 0.3.1) and skips any imported name the file also declares — those sites keep the degradation warning, which is the honest answer when the compiler cannot tell which binding a read means.
- **Type-only imports were chased with file reads and parses, and `import type { status } from './store'` bound the store's slot table into a page that only referenced a type.** `ImportBinding` now carries the specifier's `importKind` (declaration-level and inline `{ type X }`), and the signal scan skips erased bindings before any filesystem work.
- **Resolution cost scaled with import EDGES, not modules.** The lookup memo was keyed per (importing file, specifier, name), the loader had no cache, and the export walk re-parsed the defining module per name — a store imported by 17 files with 29 names was read and parsed dozens of times per build. The resolver now memoizes loader edges per (importing directory, specifier), export-walk ASTs per resolved path, and answers per (resolved path, name); the interface doc now states exactly what is cached instead of overstating it.
- **The eager import scan warned about signals on modules that contribute nothing to the page.** Any relative import pulled the whole module through the signal collector, so a util module with one internal non-literal signal produced a "renders EMPTY server-side" warning on every route that imported an unrelated helper. The scan now collects quietly; a page that actually READS an unfoldable signal still gets the use-site degradation diagnostic, which names a consequence rather than a possibility.
- **`export-resolver.ts` no longer contains raw NUL bytes.** Three cycle-guard keys embedded literal `\0` characters, which made git treat the file as binary — the 0.3.2 resolver landed as "Binary files differ" with no reviewable diff. The separators are now the `\0` escape: same runtime string, text-diffable source.

### Corrected
- The 0.3.2 changelog claimed old-style `<T>` assertions unwrap. They cannot reach the evaluator through any of this compiler's own pipelines — every parse enables Babel's `jsx` plugin, which reads `<T>` as JSX and errors first. The entry below is amended; the unwrap branch remains for callers that parse without jsx.

## [0.3.2] - 2026-08-07

### Fixed
- **A signal declared in another module had no binding, no named slot and no SSR default — the store.ts architecture Forma's own docs recommend could not fold a single signal-backed attribute, conditional or text node.** `enterComponentScope` built a module frame from the file's own program body only, so `import { ownerInviteToken } from './store'` left every read of that signal degrading to "whatever is static" while hydration papered over it — invisible unless JavaScript was off, which is when a login page matters most. gatewasm measured **158 diagnostics across 17 files**, among them a platform login page whose "Start onboarding" link server-rendered with no `href` for months while the build printed the reason on every run.

  A module's imports are now resolved to the signals they name in their DEFINING modules — through aliases (`import { x as y }`), re-export chains and `export *` barrels — reusing the export resolver's traversal (one import walker, one module loader, one cycle guard) rather than adding a second one, via a signal-flavoured `resolveExportedSignal` modelled on the constant-table resolver it sits beside. **Slot identity falls out of the frame memo:** an imported binding is resolved to the defining module's own frame and shared by reference, so however many files import a signal it is ONE slot, and a server injecting it by name reaches every reader — page and island alike. Namespace (`import * as store`) and default imports are skipped whole rather than half-resolved; a signal whose default the compiler cannot evaluate keeps today's degradation and its warning; resolution failures during the (quiet, eager) import scan change nothing at all. The 13 existing corpus `.ir` files are byte-identical — only a default that was always meant to fold now does.
- **A literal default wrapped in a TypeScript cast was refused.** `createSignal(null as string | null)` is how a store widens a signal's type — gatewasm's login store declares five signals this way — and the cast is erased at runtime, so refusing it cost the signal its slot and every binding that read it. `as`, `satisfies` and non-null `!` casts now unwrap to the literal underneath, for local and imported signals alike. *(Amended in 0.3.3: this entry originally also claimed old-style `<T>` assertions unwrap — they cannot parse under the jsx plugin every pipeline here enables.)*

### Added
- **FMIR corpus case `imported-signal-defaults`** — the store.ts shape: `store.ts` declares two signals with literal defaults, the page folds one into an href TERNARY's SSR default (the dead-link shape) and reads the other directly, and a REGISTERED ISLAND reads the same signal through a barrel that aliases it (`export { status as liveStatus }`). The golden's `@page defaults` regime carries `href="/platform/onboarding"` and `idle` in page text and island props from ONE `status` slot. It is in the Rust side's `RESOLUTION_CASES`: a relapse leaves the island a valid empty shell and the href slot defaultless, both of which `UPDATE_GOLDEN` would bless — the island-and-slots assertion fails first.

## [0.3.1] - 2026-08-06

0.3.0 was published to npm on 2026-08-06 from `compiler-v0.3.0`; these fixes ship on top of it.

### Fixed
- **Rule 9's static spread unroll could not see a constant table declared in another module, so every `...TABLE.map(item => h(…))` over an imported table shipped an empty island shell.** `...CONST.map(…)` is the compiler's escape hatch for a large static vocabulary: it expands at BUILD time into plain markup, which is what makes a 122-option `<select>` affordable on a page carrying twenty-five of them that must also work with JavaScript off. It only ever fired on a table declared in the module being walked — `extractResolvedConstants` re-extracts per resolved file, which is correct (an identifier must resolve against its own module scope) and is exactly why an IMPORTED table was invisible. The spread then fell through to `emitIsland`, and the build's only comment was "use `createList` for runtime data" about a table that is as static as data gets.

  ksx Studio's map route hit this **34 times on one page**: the key vocabulary lives in `MapPage.ts` as `KEYS_LETTER`/`KEYS_DIGIT`/…/`FUNCTIONS`, and `MapIsland.ts` imports the tables back to spread into its legend and bind-by-name selects. Every one of those 34 selects server-rendered as `<div data-forma-island>` with nothing inside it — and with JavaScript off, the no-JS write path the tables exist to provide did not exist at all. That route now compiles to **1 island (the registered `MapIsland`) and 0 fallback shells**.

  An identifier the module does not declare is now followed through its import to the module that DOES declare it, and the table is read from there — reusing the export resolver's module traversal (one import walker, one module loader, one cycle guard, one set of "why not" messages), not a second one. Scope is respected in both directions: a module's own declaration is consulted first, and a table that is shadowed by a NESTED declaration in the using file is refused rather than guessed at. The answer is memoized per name per module, so a 240 KB island asking 34 times parses the declaring module once.
- **A `const` table the file mutates in place was unrolled from its declaration-time contents.** `const` freezes the binding, not the array, so `ROWS.push(…)`, `ROWS[0] = …` and `ROWS.sort()` all left the unroll baking a stale snapshot into the server's HTML — worse than degrading, because a wrong static row is not repairable client-side while a missing island is. Mutated tables are now dropped from the constant map, for local and imported tables alike.
- **An expression written WITHOUT a `() => …` wrapper was not evaluated in either position, and the two halves failed differently.** 0.3.0 widened `evalNode` and put signal defaults into a walk-driven lexical scope chain, but only the function-wrapped forms ever called it. A page that computes its value eagerly — `h('span', null, 'Player ' + name())`, which is what the value looks like when it is read once rather than bound — hit two separate gaps:
  - **Child position** fell through the walk's child dispatch to `emitIsland`, so the element shipped as an EMPTY ISLAND SHELL: nothing server-side, nothing until the client bundle hydrated. It did warn.
  - **Attribute position** hit the props catch-all, which minted `attr:<key>` with **no default and no diagnostic**. The attribute went out with no value, the island table looked clean, and the build log was empty. This is the more dangerous half: an empty-default slot is a perfectly well-formed slot, so nothing short of rendering the page shows the hole — and the client does not repair it either, because hydration skips a prop whose value is not a function as "static and already in the SSR HTML". The attribute never appears at all. It is what stripped the tooltips off ksx's controls, unnoticed, for the entire life of that UI.

  Both positions now fold through the SAME `evalNode` and the same signal scope chain as the wrapped forms — no second evaluator. A foldable child becomes a `DYN_TEXT` slot carrying its SSR default; a foldable attribute value becomes a typed attribute slot (`TYPE_BOOL` for a boolean, so an eagerly-computed `disabled` is omitted rather than shipping `disabled="false"`, which the browser reads as DISABLED). Values stay TYPED through evaluation: `'Slot ' + count() + ' ready'` over `createSignal(3)` renders `Slot 3 ready`.
- **A bare signal read in child position shipped an island named after the signal.** `h('span', null, name())` reached the sub-component resolver, which cannot find a file for `name` and emitted an `ISLAND_START name` shell — an island no client registry can hydrate. It now binds the signal's own slot, exactly as `() => name()` does.
- **`String(x)` / `Number(x)` in child position islanded as a component.** The callee is capitalized, so the component path claimed it. Both now fold when their operand does.
- **A TypeScript annotation was enough to degrade an otherwise evaluable expression** — the walker reads original `.ts` source, so `('Slot ' + count()) as string` and `name()!` arrived with the cast still attached and `evalNode` refused them.
- **A child that evaluates to `null`, `true` or `false` now emits nothing, instead of an empty island shell.** `h()` drops those children outright, so `ready() && 'Go'` with `ready` defaulting to false put an empty `<div>` on the server-rendered page that the client had no counterpart for. This extends the existing null/undefined/false rule to the forms that only become null or boolean after evaluation.

### Added
- **A spread whose table cannot be read now names the table's OWN module and what about it is not static.** The old line pointed at the spread and suggested `createList`, which sends the author to the wrong file when the table is one module away. A degraded spread now reports the declaring file plus the actual cause — built by a call at runtime, declared `let`, elements that are not object literals of primitives, mutated in place, never exported, reached through a namespace or default import, imported from a package, a specifier that resolves to no file on disk, or a re-export cycle. Every one of those still degrades to an island; none of them is silent, and none of them hangs.
- **FMIR corpus case `imported-const-table`** — the ksx shape: a page module that declares its tables as bare `const` + `export { … }`, a REGISTERED ISLAND that imports them back across an inert page↔island cycle, and a third table reached through a barrel that aliases it (`export { MOD_KEYS as MODIFIERS } from './modifiers'`). Rows are substituted in child and attribute position, and one row's value needs HTML escaping. It is in the Rust side's `RESOLUTION_CASES`, so a relapse fails on the minted `island_<n>` before the golden diff is read — the golden alone would not catch it, because an island shell is perfectly valid FMIR that `UPDATE_GOLDEN` would happily bless. The twelve existing `.ir` files are byte-identical.
- **Diagnostics for the rest of the silent attribute paths.** The audit behind the fix above enumerated every expression form that can appear in an attribute value and every prop shape, and found the whole class silent: concatenations, template literals, calls, conditionals, `&&`/`||`, object literals (a `style` object), array literals and `new` expressions all minted an empty attribute slot without a word. So did four prop shapes that dropped attributes outright — `{...spread}` props, a computed key, a method-valued prop, and a props ARGUMENT that is not an object literal (`h('div', props, …)`, which silently dropped *every* attribute on the element) — and `dangerouslySetInnerHTML`, whose markup is deliberately not server-rendered but whose absence was never reported. All of them now warn with the file, the construct in source terms, and the consequence. The consequence text is also corrected: a degraded attribute is stated as PERMANENTLY missing, not missing-until-hydration, because that is what actually happens to a non-function prop value.
- **A behavioural completeness test for the attribute half of the diagnostics contract** (`tests/ir-diagnostics.test.ts` > "never leaves an attribute empty without saying so"). The island half can be checked statically by enumerating `emitIsland` call sites; a degraded attribute is emitted by the same `addSlot` line as a healthy one, so it is checked by driving every expression form through the walker and requiring that any attribute which will be missing from the HTML was reported. It fails on 16 forms against 0.3.0.
- **`evalNode` folds the remaining unambiguous operators** — `-`, `*`, `/`, `%` and the relational operators over same-typed operands, and strict `===`/`!==`. Loose `==`/`!=` is deliberately NOT folded: its coercion table depends on telling JS `null` from `undefined`, which this evaluator spells as the same value, and a fold that guesses there would put the wrong branch or attribute on the page instead of warning.
- **FMIR corpus case `eager-concat`** — concatenation in child and attribute position, including a multi-operand concat mixing a string and a NUMBER, walked by the real Rust reader with the render pinned to a golden. Its `@page defaults` section is the check that matters: `Player Xbox`, `title="Enable Xbox"`, `title="Slot 3 ready"`. Before this change that section would have been an empty island shell and two valueless attributes — all of it structurally valid FMIR that every other assertion in the suite accepts. The eleven existing `.ir` files are byte-identical.

## [0.3.0] - 2026-08-06

### Fixed
- **Signals were only found in scopes someone had written an extractor for.** Signal defaults were gathered by a PRE-PASS that enumerated scopes BY HAND — one method per shape: the root page's function body, island component files, inline-mount entries — and merged them into one flat `Map<name, default>` before the walk started. The WALK independently decided what actually got inlined into the page. Every time the walk learned to inline something new, the pre-pass had to be taught the same thing separately, and when it was not, the failure was SILENT: the signal kept its binding but lost its name, its slot and its SSR default. Four scopes were affected, all of them ordinary: **an inlined sub-component's body**, **the module scope of an inlined sub-component's own file** (the reason `barrel-exports` worked at all was that its chip is a registered *island*), **the root page file's own module scope**, and **anything below the top level of a scope** (`if`/`try`/loop/block). Extraction is now driven by the walk itself (`src/signal-scope.ts`): the walk pushes a lexical frame at each point it enters a new scope, and lookup searches outward through the chain. The invariant that replaces the list of shapes — *if the walk inlined the code, its signals are in scope; if it did not, there is nothing to name* — has no list to keep in sync, so a construct the walk learns to inline later gets its signals for free. `extractSignalDefaults`, `extractIslandSignalDefaults`, `extractInlineMountSignalDefaults` and the first-wins island merge are gone.
- **Every conditional rendered its ELSE branch server-side, and hydration did not repair it.** `SHOW_IF` slots carried no SSR default, so the walkers read them as false. A `createShow(() => visible(), …)` whose signal defaults to `true` server-rendered the hidden branch — and stayed that way after hydration: `adoptShowRegion` matches the client's THEN descriptor against the server's ELSE element, the tags match, `adoptNode` takes the server's node, and the static class and text are never rewritten. Both mismatch-repair arms test "one side has content and the other does not", and when both branches produce content neither fires, so nothing warns. The page showed the wrong branch until the signal CHANGED VALUE — for a config-like default that never changes, forever. `show:*` slots now carry the branch the client would take, evaluated from the signals in scope; the slot NAME and the separate `show:*` slot are unchanged, because servers inject shows by that name.
- **Dynamic text children never got an SSR default at all.** Only `DYN_ATTR` computed one, so `h('p', null, () => count() + ' items')` shipped the zero-width-space placeholder and the text appeared only after hydration. Text bindings now evaluate the same way attributes do.
- **A boolean-valued dynamic attribute was written as the STRING "false".** `disabled: () => !!busy()` minted a `TYPE_TEXT` slot with default bytes `"false"`, which renders `disabled="false"` — a DISABLED control, the exact inversion of what the client shows. A binding that evaluates to a boolean now gets a `TYPE_BOOL` slot, which the walkers omit when false and write bare when true.
- **`createSignal(-1)` and `createSignal(SOME_CONST)` got no named slot.** A signed numeric literal is a `UnaryExpression` in the AST, and an identifier naming a module string const was rejected as "not a literal" — so declaring a default once as a `const` and reusing it cost the signal its slot. Both now evaluate, as do expression-less template literals and a zero-argument `createSignal()` (which is `undefined` on the client, i.e. the null default).
- **Every `.tsx` page compiled to placeholder IR.** esbuild rewrites `export function Page() {…}` into `function Page() {…}` + `export { Page };`, and all three copies of "find the function this module exports under this name" read only `ExportNamedDeclaration.declaration` — the one form esbuild never emits. So a JSX root page resolved to nothing, `generateRealIr` returned null, and the plugin fell back to `<div id="app" data-forma-page="…"></div>`: no slots, no islands, zero server-rendered content, build exit code 0. The single line it printed (`could not find return h() tree in Page`) named the wrong cause and did not mention the consequence. The three copies (`parseComponentFile`, `findExportedFunctionBody`, `resolveSubComponent`) are now one resolver (`src/export-resolver.ts`) that handles declaration exports, export SPECIFIERS (`export { X }`, `export { XImpl as X }`, and specifiers forwarding an imported binding), `export default`, cross-file re-exports (`export { X } from './x'`, `export * from './x'` — index barrels), aliased imports at the call site (`import { CardImpl as Card }`), and — for same-file calls only — non-exported and function-scoped declarations. See *How a component is found* in the README for the full table, including the forms that are deliberately NOT followed and warn instead.
- **`.tsx` islands silently lost their signal defaults.** The same blind spot in `findExportedFunctionBody` had no warning at all: byte-identical `Counter.ts` and `Counter.tsx` islands produced different IR — the `.ts` one a named `hits` slot with default `"42"`, the `.tsx` one an anonymous `text:0` with no default — and nothing in the build log said so. Server-side injection by name then failed at runtime. An unresolvable component now warns; and when a barrel forwards the export, module-scope signals are read from the file that actually declares it rather than from the barrel.
- **Components imported by a PAGE file were invisible.** The import map was built once from the ENTRY point and captured in a closure that every nested walk carried unchanged (walk contexts are spread-copied), so a component `pages/OverviewPage.tsx` imported became an empty island shell unless `app.tsx` happened to import it too. `WalkContext.resolveComponent` now takes the file the CALL is in and rebases on that file's imports.
- **`mount(() => h('div', …), '#app')` dropped the whole page to placeholder IR.** `h` is an imported identifier, so the named-component pattern claimed it and the plugin went looking for a component file called `formajs`. An expression-bodied `mount()` arrow is now an inline mount, whose body is the tree — as is `mount(() => LocalPage(), '#app')` over a component declared in the entry file.
- **An inline-mount entry got ZERO named signal slots.** The plugin asked for an exported function literally named `__inline__`, a lookup that could never match, so module-scope `createSignal`s on a `mount(() => { … })` page never became named slots and every binding to them landed in an anonymous `text:`/`attr:` slot that `SlotData::from_json` cannot address. An inline mount's scope chain is now the entry file's module scope plus the mount callback's own body, opened by the walk like every other scope.
- **A numeric signal on an inline-mount page lost its type and default.** The two mount paths carried separate copies of slot registration and the inline one handled only text and bool, so `createSignal(11)` became a `TYPE_TEXT` slot with empty `default_bytes`. There is now one encoder (`signal-scope.ts`), used wherever a signal slot is minted.
- **Fragment children that were not `h()` calls or string literals were silently DROPPED** — `h(Fragment, null, h('p', null, 'a'), () => name())` emitted the paragraph and nothing else: no opcode, no island marker, no warning, and no way for the client to recover the missing binding because there was no marker to hydrate. Dynamic text, numbers, ternary shows, `createShow`/`createList` calls and spreads were all affected, in both the `h(Fragment, ...)` and bare `Fragment(...)` forms. Fragment children now go through the same `emitChild` path as an element's children, and a parameterised test requires the two to emit identical opcodes.
- **A component tag (`h(Card, ...)`, which is what JSX compiles `<Card/>` to) produced an ANONYMOUS island** — `island_0`, discarding the component name. Since the client registry is keyed by component name, that island could never hydrate: the page was left with a permanently empty `<div>`. Capitalized identifier tags now route through the same sub-component/island path as a `Card(...)` call, so they are inlined when resolvable and registered under their real name when not. Lower-case identifier tags (a runtime tag name) still emit a dynamic-tag island, now with a warning.
- **Call-site props were never substituted into an inlined sub-component.** The helper that claimed to do it returned its input unchanged on every path, so `Badge({ label: 'New' })` over `function Badge(props) { return h('span', null, props.label) }` inlined the span and then emitted an empty island where the label should be — the text absent from the server render with no diagnostic. Literal props are now substituted for both binding forms (`props.label` and destructured `{ label }`, including `{ label = 'fallback' }`), in attribute and child positions, skipping any name a nested function rebinds.
- **The static spread unroll (Rule 9) never substituted item properties in ATTRIBUTE position.** `...NAV.map(item => h('a', { href: item.href }, item.label))` substituted the label but passed the props object through untouched, so every row rendered `<a>` with the href missing and a slot that no runtime data would ever fill — the same silent missing-attribute shape as ledger finding #10. Substitution now descends into object expressions.
- **`formaCompiler`'s include/exclude patterns did not match anything they claimed to.** Exclude tested `id.includes(pattern.replace(/\*\*\//g, ''))`, i.e. `id.includes('node_modules/**')`, which is false for every path that exists — so the default exclude never excluded and the plugin rewrote dependency sources. Include compared only the pattern's file extension, so a scoped `include: ['src/**/*.ts']` also claimed `vendor/x.ts`. And Windows module ids (backslash-separated) matched no pattern at all. Both are now real anchored glob matches (`**` = any number of segments, `*` = within a segment) over an id normalized to `/` with any Vite query suffix stripped. Projects that were relying on `.js`/`.jsx` being transformed must list them in `include` — the documented default has always been `.ts`/`.tsx` only.
- **An island subtree that threw mid-walk left the bytecode unbalanced** — `ISLAND_START` had been emitted, and the failure path registered a *second* island and emitted a nested shell instead of closing the first. The failure is now absorbed inside the span: the diagnostic names it and `ISLAND_END` still closes the island.

- **Duplicate `attr:` and `text:` slot names on any page that binds the same attribute key twice, or has two dynamic text children at the same child index** — the per-page `#n` occurrence registry introduced for list and show slots was never extended to the other two slot-name families. `h('div', { id: () => a() }, h('span', { id: () => b() }))` emitted two slots both named `attr:id`; two sibling `<span>`s each with a single dynamic text child emitted two slots both named `text:0`. The Rust loader builds `name_to_slot: HashMap<String, u16>` by inserting every name (`forma-ir/src/slot.rs`), so duplicates collapse and one of the two becomes permanently unreachable for server-side `SlotData` injection. WHICH one survives depends on the reader: `forma-ir` <= 0.1.4 was last-insert-wins, while 0.2.0 resolves first-in-table-order consistently (`from_json` and `slot_id_by_name` used to disagree with each other). If you are migrating an injection key that was duplicated, check against the `forma-ir` version you actually run — silently, with no build error. `attr:` and `text:` now run the same page-wide occurrence registry as list and show, created eagerly on the root walk context and shared by reference into island subtrees, inlined sub-components, list bodies and show branches. First occurrence keeps its exact former spelling (`attr:id`, `text:0`); later ones get `#2`, `#3`. Server code that injected a duplicated key reached the FIRST occurrence under `forma-ir` 0.2.0 and the LAST under 0.1.4 and earlier; the first occurrence keeps the unsuffixed key, so code that meant a later one must now use its suffixed key.
- **Duplicate slot names when the first list/show sat inside a nested walk context** — the per-page list/show name registries were created lazily on the *current* context, but island subtrees, inlined sub-components, and list bodies walk spread copies of it. If the first `createList`/`createShow` for a given base name lived inside such a copy, the registry died with the copy and a later sibling recreated it, minting duplicate names (`list:todos:array` twice, `show:visible` twice) that collapse in the Rust name→id map (the first wins in `forma-ir` 0.2.0, the last in 0.1.4 and earlier) — and the outcome was document-order dependent. Registries are now created eagerly on the root walk context and normalized at the walk entry points, so suffixes (`#2`, ...) are page-wide in document order regardless of nesting.
- **Island slot-capture stack now stays balanced when an island subtree walk throws** — a resolution failure mid-walk used to leak the capture set, making an enclosing island record the failed inner island's (wrong) slot ids.
- **Per-item list scratch slots (`list:<base>:item`) are excluded from island `slot_ids`** — they hold the LAST rendered row after SSR, so serializing them into `data-forma-props` leaked that row into the page. All other families (named signals, `attr:*`, `text:*`, `show:*`, `list:*:array`, `list:*:<prop>`) are still captured; the key-space contract is documented in the README.
- **`export const` declarations are now visible to module-level extraction** — string-constant folding, file-constant arrays (Rule 9 unroll), and module-level island `createSignal` defaults previously only saw bare `const` statements and silently ignored exported ones.
- **`activateIslands({...})` is scanned on every entry-point pattern** — a block-body `mount(() => { ... return h(...); })` entry never populated island names at all, so its islands were inlined instead of emitting `ISLAND_START`/`ISLAND_END`.
- **Sub-component constant re-extraction falls back to empty maps on parse failure** — it previously fell back to the *parent* file's constants, resolving the child's identifiers against the wrong module scope.
- **`function` expressions derive binding names** — `createShow(function () { return visible(); }, ...)` now yields `show:visible` (previously silently positional); block-body arrows unwrap too. Applies to list sources as well.
- **Module consts shadowed in any nested scope are no longer folded** — a component-local `const cls = computeClass()` shadowing a module `const cls = 'icon'` used to bake the module value into a static attribute with no slot, unrecoverable client-side. Shadowed names now take the correctable dynamic-attribute path with the existing build warning. The check is deliberately over-conservative (any nested declaration or parameter of the same name suppresses folding).
- **64KB string guards** — a folded const over 65535 UTF-8 bytes is dropped from folding with a warning (FMIR string-table entries have a u16 length prefix), and the binary emitter now throws a descriptive error instead of silently wrapping the length and corrupting the string/slot tables; `generateRealIr` catches that and falls back to no-IR with a warning.

### Changed
- **Breaking: slot tables change on any page with signals in a newly-read scope.** A binding to a signal that is now in scope reuses that signal's named slot instead of minting an anonymous one, so `attr:`/`text:` names DISAPPEAR and the `#N` suffixes on the survivors renumber; one new name appears per newly-discovered signal; and slot ids reorder, because signals are minted where the walk enters their scope rather than all up front. Measured over the shipped corpus: `dynamic-text` traded four `text:*` names for `headline`/`subhead`/`count`/`badge`; `dynamic-attrs` lost `attr:value` (its `value: () => query()` now reuses `query`) and gained `busy`/`tone`/`query`; `create-show` and `ternary-asymmetric` gained their condition signals. Slot IDS are safe to reorder — the client matches hydration markers positionally and `DYN_TEXT` carries its own `marker_id` — but slot NAMES are the injection contract. Unknown keys fail soft in `SlotData::from_json`, so a stale key is silent: re-check injected names against the emitted string table after upgrading.
- **Breaking: a page "twin" declaration of an island's signal is now a separate slot.** Re-declaring an island's signal in the Page component (the workaround for the old extractor) is a different lexical binding — which is what it is at runtime too — so it gets its own slot and pushes the island's own to `#2`. Delete the twin; the island's declaration is what the walk reads. The rename warns.
- **Signal name collisions across scopes are resolved by the shared occurrence scheme.** Two components can each declare `count`; the first scope the walk enters gets `count`, the next gets `count#2`, in the walk's document order. One slot per DECLARATION SITE: a component inlined or islanded twice shares its signals' slots. Every suffixed name is reported at build time.
- **Breaking: show slots now get condition-derived names** — every `createShow` previously emitted a slot literally named `show:createShow` (and ternary conditionals `show:<index>`), so at most one show per page was addressable by name. Shows now use the same naming scheme as lists: the base derives from the condition (`createShow(() => visible(), ...)` → `show:visible`; arrows, calls, member access, and `!`-negation unwrap), with a positional fallback (`show:#2`) and per-base `#n` occurrence suffixes in document order (first occurrence unsuffixed).
- **List slot names for literal sources now use the map parameter** — when the data source has no derivable name (e.g. `createList(() => [], ...)`), the map function's first parameter names the list (`(tile) => ...` → `list:tile:array`) instead of the positional `list:#N:array`; the positional fallback remains for `_`/unnamed params.
- **Migration**: server code injecting `"show:createShow"` must switch to the name-keyed scheme (`"show:visible"`); literal-source list keys change from `"list:#N:array"` to map-param-derived where a named param exists. Slot names are visible in the emitted `.ir` string table; unknown keys are silently ignored by `forma_ir::SlotData::from_json`, so stale keys fail soft — check names after upgrading.
- Sub-component and island subtrees now resolve file-level constants against their **own** module scope (re-extracted from the resolved source) instead of the root file's constants.

### Removed
- **Breaking: the SSR plugin no longer writes `<page>.islands.json`.** It was build metadata deposited into the *served* asset directory, unhashed, so it lingered in the output and was picked up by asset-embedding servers; its only consumer was `@getforma/build`'s island-registry generator, itself removed as unusable. The island table is inside the `.ir` binary, and `generateRealIr()` returns it as `{ binary, islands }` for programmatic callers.
- **`emitIr` is no longer exported** — it and its private `emitNode` helper were a second, divergent AST→opcode implementation with no consumer anywhere in this repo or the downstream ones: the real pipeline has always gone through `walkHTree`/`walkCallExpression`. `emitNode` predated the slot-name occurrency registries entirely (it minted raw `attr:<key>` / `text:<i>` names) and understood none of createShow, createList, islands, Fragments or sub-component resolution, so anything that had adopted it would have produced subtly wrong IR. Use `generateRealIr` (or `walkHTree` with an `IrEmitContext`) instead. `IrEmitContext` itself is unchanged and still exported.

### Added
- **`tests/ssr-render.test.ts` — the property, not the mechanism.** Slot names and default bytes are how correct SSR is achieved; they are not what was broken. A missing default is a perfectly well-formed slot table, which is why every slot-level test passed while these pages shipped wrong. Each case compiles a real project off disk, renders the emitted FMIR under its own slot defaults (what a server sends before injecting anything), and compares the MARKUP to what `@getforma/core` builds on the client — the truthy `SHOW_IF` branch, text and attributes from each newly-read scope, a numeric `0` (which "no default" is indistinguishable from), a bare boolean attribute, and a template-literal class. Nine of its thirteen cases fail if the walk's scope hook is removed.
- **FMIR corpus case `sub-component-scopes`** — signals in the four scopes the old extractors did not look in, the same-name collision rule, and a `createShow` whose condition defaults to `true`. Its `@page defaults` golden was, before this change, four zero-width spaces, a missing class, a missing boolean attribute and the wrong `SHOW_IF` branch.
- **`tests/signal-scope.test.ts`** — the scope machinery at unit level: what counts as a literal default, which statements belong to a scope (into blocks, never into nested functions), shadowing, collisions, frame reuse, and where a nested helper's chain hangs.
- **A dynamic attribute, dynamic text child or conditional whose expression cannot be evaluated now warns**, naming the file, the binding and what the page loses. A conditional's warning says the server renders the ELSE branch and that hydration will adopt it silently if the client disagrees.
- **`evalNode` widened to the expressions real pages use** — template literals WITH embedded expressions (the create-forma-app dashboard writes its sidebar class this way, and the whole nav was shipping with no `class` attribute at all), `&&`/`||`, and block-bodied arrows whose own `const` locals fold. Values stay typed through evaluation instead of being stringified, so `0` is falsy and `false` is not the truthy string `"false"`.
- **Two FMIR corpus cases that mirror what a real project produces**, `jsx-page` (an all-`.tsx` app — entry, page, sibling sub-component and island, every one arriving through esbuild's export rewrite) and `barrel-exports` (every component reached through an `index.ts` barrel). Both were total losses before the resolver fix and neither could have been caught by the old suite: all 22 fixture files were `.ts`, `.tsx` appeared only as a hand-written filename label on already-transformed source, and no test anywhere asserted that emission had NOT fallen back to the placeholder. The Rust contract test (`resolution_cases_ship_named_islands_over_named_slots` in `forma`) requires their islands to carry real component names rather than a minted `island_<n>`, to carry non-empty slot ids, and the page to have slots named after its signals carrying their defaults — claims the golden HTML cannot make, because a degraded emit is still a valid, walkable module. The existing eight `.ir` files are byte-identical.
- **`tests/ssr-emission.test.ts`** — `generateRealIr` over real files on disk, which is the level the suite was blind at. Every assertion goes through a helper that first proves the emit is not the placeholder shell.
- **Build diagnostics for every silent degradation.** The pattern behind most of the ksx dogfood findings was "the compiler could not understand a construct, emitted a placeholder, and said nothing". Every fallback path now warns with the file, the construct in source terms, and the consequence for the rendered page: dynamic tags, untranslatable children (bare identifiers, template literals, unwrapped ternaries and `&&`), un-unrollable spreads, each `createList` bail-out, non-`h()` `createShow` branches, components that cannot be resolved / are recursive / exceed the inlining depth / are passed non-literal props / have no followable return, islands whose content will not compile, and `createSignal` initial values that are not literals (which is why the signal gets no named slot — ledger finding #9's cost, previously invisible). Diagnostics name the *resolved component's* file, not the page that included it. A page the compiler fully understands emits nothing, and a test enumerates the fallback call sites in the walker so a new one cannot be added without a diagnostic.
- **Island table entries now carry real `slot_ids`** — every slot referenced inside an island's SSR span (dynamic attrs, signal-bound text, list slots, reused page-level signal slots, nested islands) is captured and written to the island table, which was previously always empty. The `forma-ir` Rust walker skips props emission for islands with empty `slot_ids`, so with this populated it natively emits `data-forma-props` and the `__forma_islands` script block — consumers hand-emitting that script block server-side can migrate to the native path.
- **Module-level string constants fold into static attributes** — a top-level `const` initialized with a string literal, expression-less template literal, `+` concatenation chain, or reference to an earlier string const resolves at compile time when used as an attribute value (`d: ICON_PATH` → static attr, no slot), and folds inside function-valued props when computing SSR defaults.
- **Build warning for statically unresolvable identifier attributes** — an attribute value that is a bare identifier or member expression the compiler cannot resolve now warns at build time instead of silently rendering the attribute empty in SSR.

## [0.2.0] - 2026-08-05

### Changed
- **Breaking: list slots now get unique, per-list names** — previously every `createList` emitted slots named `list:array` / `list:item` / `list:<prop>`, so on pages with more than one list only the first was reachable by name and server-side `SlotData` injection could not target the others. Each list now derives a base name from its data source (`createList(todos, ...)` → `todos`; arrows, calls, and member access unwrap to the underlying name), deduped per page with `#n` suffixes and a positional fallback (`#3`) when no name is derivable. Slots are emitted as `list:<base>:array`, `list:<base>:item`, and `list:<base>:<prop>`.
- **Migration**: server code injecting `"list:array"` must switch to the named key, e.g. `"list:todos:array"`. Slot names are visible in the emitted `.ir` string table; unknown keys are silently ignored by `forma_ir::SlotData::from_json`, so stale keys fail soft — check names after upgrading.
